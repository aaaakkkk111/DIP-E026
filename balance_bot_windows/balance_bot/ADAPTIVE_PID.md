# 情境自适应 PID：神经网络 + PPO，跑在 STM32 上

小车按当前局面（负重、坡道、台阶跌落、冲击）自己改 PID 增益。网络在电脑上用
PPO 训，量化成定点后搬到板子上。

    训练     python scripts/train_adaptive_pid.py --steps 300000 --n-envs 8
    导成 C   python scripts/export_nn_c.py runs_stm32/adapt_01.npz
    自检     python tests/test_adaptive.py

---

## 1. 板子装得下吗：装得下，占 3.6%

F103RC，256 KB flash / 48 KB RAM，现有固件占 54.6 KB ROM、17.3 KB RAM。

| | 大小 |
|---|---|
| 权重 21-32-32-6（int16） | 3776 B |
| 偏置（int32） | 280 B |
| tanh 查找表 | 130 B |
| 增益查找表 6×129（float） | 3144 B |
| **Flash 合计** | **7.2 KB = 剩余空间的 3.6%** |
| RAM 静态 + 栈 | 488 B = 剩余空间的 1.6% |

算力：每次推理 1888 次乘加，25 Hz 调用。

**必须定点**。F103 是 Cortex-M3，**没有硬件浮点**：同一个网络用软件浮点单次
要 4.5 ms，会挤掉 200 Hz 主环的预算；定点 0.08 ms。所以网络走 Q11 整数，
只有特征提取那十几次运算留在 float（200 Hz 下也只占千分之几）。

## 2. 车怎么知道自己在什么局面：8 个特征

`balance_bot/firmware/features.py`。全部是 IIR，**不用 FFT、不留历史缓冲**，
9 个标量状态，每行都能原样搬到 C。输入只有固件看得见的量：卡尔曼角度、陀螺、
加速度计两轴、编码器、速度环积分、自己写出去的 CCR。

| 特征 | 是什么 | 认哪种局面 |
|---|---|---|
| `bp31` | 31 Hz 带通能量 | 负载档位。**必须带通**，高通会把 4.3 Hz 死区极限环一起收进来 |
| `gyro` | \|陀螺\| 慢 EMA | 激励水平 |
| `shock` | \|陀螺\| 快峰值保持 | 冲击、磕碰 |
| `freefall` | \|a\|/g − 1 | 悬空趋近 −1，落地冲正 |
| `tilt` | 角度慢 EMA | 坡度代理量 |
| `venc` | 编码器速度 EMA | 在跑还是站着 |
| `vint` | 速度环积分 | 坡道、持续外力、被拖拽 |
| `duty` | \|CCR\|/满量程 EMA | 用掉多少力矩权限 |

四个情境在各自通道上分得很开（`tests/test_adaptive.py` 钉死了这一点）：

| 情境 | 峰值 shock | 峰值 freefall | 峰值 vint |
|---|---|---|---|
| 静止 | 0.21 | 0.07 | 0.01 |
| 冲击 | **1.08** | 0.15 | 0.05 |
| 跌落 | 0.35 | **7.16** | 0.04 |
| 坡道 | 0.26 | 0.47 | **0.60** |

**为什么必须有这 8 个**：只看瞬时状态的话，「压了 3 kg」和「在上坡」长得一样
——两者的俯仰角都是偏一个常值。

## 3. 情境怎么造出来

`balance_bot/scenarios.py`，每个都落到物理上：

| 情境 | 实现 | 幅度（难度 1.0） |
|---|---|---|
| 负重 | 改底盘质量/质心/惯量，可开局挂上也可中途压上 | 0.5–4 kg |
| 坡道 | **转重力向量**，不建坡道几何 | ±2–12°，0.5–2 s 渐变 |
| 台阶跌落 | 整体抬高再松手，落地交给接触模型 | 1–5 cm |
| 冲击 | `fire_impulse`，和 GUI 踢击同一条路 | 2–9 N × 30–80 ms |

坡道用转重力是故意的：对滚动的车来说，绕 y 轴转重力和把地面倾斜等价，省掉
一套没标定过的坡道接触几何。代价是视觉上车还在平地，且等价关系只对平面成立。

冲击上限压在 9 N 是有依据的：孪生实测原厂模式 1 扛得住 8.5 N、9 N 倒，而物理
上限（最优控制）是 11.6 N。再往上是**物理上也救不回来**，不是策略的问题。

## 4. 训练

`scripts/train_adaptive_pid.py`。复用 `STM32Env` 已有的有界乘性增益空间、
变化率限制和七项线性奖励，加两项情境奖励（坡上别下溜、落地冲击）。

三条规矩都是为了「能上车」：

1. **默认不做观测归一化**。VecNormalize 的滑动均值方差会变成板子上另一组必须
   同步的常数，而特征本来就缩放到 ±1 附近了。要开加 `--obs-norm`。
2. **网络小**，默认 32×32。
3. **训完自动量化复评**：脚本最后用定点网络重新打分，float 和 q15 两个成绩
   并排打出来。**上车跑的是定点网络，所以定点网络才是该看的那个分数。**

## 5. 上车怎么接（三行）

```c
NN_Init();                                    /* 上电一次 */
NN_Feed(angle, gyro, acc_fwd, acc_up,         /* 每个 200 Hz 控制拍 */
        v_enc, ccr, encoder_integral);
if (NN_Apply(&Balance_Kp, &Balance_Kd, &Velocity_Kp,
             &Velocity_Ki, &Turn_Kp, &Turn_Kd)) { /* 每 8 拍 = 25 Hz */
    /* 用新增益 */
}
```

四道护栏，任何一道不过就**保持原厂增益不动**：

1. 动作硬钳到 [−1, 1]
2. 变化率限制 `a = 0.7·上一步 + 0.3·本次`（和训练时同一条公式）
3. 算出的六个增益逐个查范围，**有一个越界就整组不写**
4. 看门狗：`NN_Feed` 停超过 40 拍（0.2 s），或 `NN_Enable(0)`，直接不写

## 6. 怎么保证板子上跑的和孪生里训的是同一个东西

`tests/test_adaptive.py` 会把生成的 C 用 gcc 编出来，和 Python 逐帧对拍：

| 项 | 实测 |
|---|---|
| 特征 | 最大差 1.0e-6（float 舍入量级） |
| 增益 | 最大相对差 0.69% |
| 量化误差 | 动作量程的 0.95%，RMS 0.28% |

增益那 0.69% 是数值差不是逻辑差：C 侧特征算在 float32、Python 在 float64，
输入差一个 Q11 的 LSB，经网络放大到动作约 3e-3，再经 turn_kp 那一维 span=7
的指数映射放成千分之几。

**开发时踩过的两个坑，都写在代码注释里了：**

* **C 里累加器必须 64 位。** 权重顶到 int16、输入 Q11 最大 8×2048，单项乘积
  就有 5.4e8，32 项累加到 1.7e10，int32（2.1e9）直接溢出——输出是翻车不是
  略偏。这个 bug 曾让 C 和 Python 的增益差 124%。
* **`printf("%d %g", NN_Apply(...), kp, ...)` 是错的。** C 的函数参数求值顺序
  未定义，gcc 先取 `kp` 的旧值，对拍结果整整差一拍。必须先调用再打印。

## 7. 已知的限制（别按错误前提用）

孪生只在模式 1 静止那个角落标定过：**轮速峰值 5.5%、PWM 权限 2.7%、0 负重、
只有模式 1**（TWIN_BASELINE.md 第 10.4 节）。这四个情境全在角落外面：

| 情境 | 孪生在这里的状态 |
|---|---|
| 冲击 | 已实测：受激幅度只有真车 60–70%，共振频率低 20% |
| 负重 | 重新拟合后没验过；缺电池内阻压降模型，越重越乐观 |
| 坡道 | 地面 μ 在静止工况辨识不出来，0.90 是按花纹橡胶胎的物理值定的 |
| 跌落 | 接触刚度 solref/solimp 从没标定过 |

训练默认开着域随机化（`randomize=True`）和难度课程，靠的就是"策略别依赖某个
具体数值"。但域随机化能覆盖的是**参数的不确定性**，不能覆盖**结构缺失**
（比如电池压降、坡道接触）。所以：

**趋势可信，绝对值不可信。** 上车前建议先做 TWIN_BASELINE.md 第 10.7 节那三个
测量（定速台阶、直线跑偏、负重转向），把力矩-转速曲线和左右不对称标定上。
