# STM32 平衡小车数字孪生

对亚博 STM32 平衡小车固件的忠实复现，用来给 RL / LLM 调出来的参数提供一个
**可比的 baseline**：同一套物理、同一套扰动、同一批种子，指标是**存活步数**。

所有常数都标注了出处，可以逐条核对：

| 来源文件 | 提供了什么 |
|---|---|
| `6.LQR/Matlab/parameter_LQR.m` | 质量、惯量、轮径、轴距、质心高度 |
| `6.LQR/STM32_code/APP/app_control.c` | LQR 控制律与 6 个增益、机械零位、遥控目标值 |
| `6.LQR/STM32_code/APP/app_motor.{c,h}` | PWM 死区、编码器标定、40° 关机保护 |
| `6.LQR/STM32_code/APP/KF/KF.c` | **姿态卡尔曼滤波（现已逐行复现）** |
| `6.LQR/STM32_code/BSP/MPU6050/mpu6050.c` | 陀螺/加速度量程、`DEFAULT_MPU_HZ` |
| `6.LQR/STM32_code/BSP/MPU6050/DMP/inv_mpu.c` | **片上 DLPF 实际被设成了 98 Hz** |
| `6.LQR/STM32_code/USER/main.c` | `GET_Angle_Way = 2` → 走卡尔曼那条分支 |
| `4.Balanced_Car_base/04.bluetooth_control/.../pid_control.c` | 默认三环 PID 增益 |
| 全树 24 份 `pid_control.c` | **各工程的 PID 增益并不相同**，见第 6 节 |
| `6.LQR/STM32_code/BSP/bsp.c` | PWM 定时器 25 kHz / 周期 2880 |

> **2026-09 更新。** 这一版重新通读了 `sourcecode/` 全树，改动集中在传感器链路：
> 板子上真正在跑的那个卡尔曼滤波被找出来并逐行复现了，MPU6050 的片上 98 Hz

## 1. 怎么用

```bash
cd ~/balance_bot && source .venv/bin/activate

python tests/test_twin_baseline.py                       # 50 项自检，只需 numpy
python scripts/bench_twin_baseline.py --episodes 40      # 两套原厂固件的 baseline

```

```bash
python scripts/sim_gui.py            # 或 python -m balance_bot.ui.sim_gui
```

|---|---|---|---|---|

| 0.25 | **500.0** | **500.0** | 500.0 | 500.0 |
| 0.50 | 374.0 | **486.8** | 450.5 | 500.0 |
| 0.75 | 256.7 | **305.6** | 253.1 | 476.3 |
| 1.00 | 155.8 | **190.4** | 150.4 | 352.1 |

复现命令：`python scripts/bench_twin_baseline.py --imu kalman --episodes 40`
（`--imu lag` 出右边两列）。

**结论变了一半。** 「原厂 PID 比原厂 LQR 抗扰」还成立，但**优势从 2 倍缩到
了 1.2 倍**（难度 1.0 档：190 vs 156，旧模型下是 352 vs 150）。

差别几乎全部落在 PID 那一列，原因很具体：PID 工程把 `Gyro_Balance`——
**未经任何软件滤波的 16 位陀螺寄存器原值**——直接喂给 `Balance_Kd`。旧的占位
模型顺手给它做了一次一阶低通，等于白送了 PID 一个它在真车上没有的滤波器。
新版按固件原样喂原始寄存器值（含量化，含片上 98 Hz DLPF，不含别的），
PID 的微分项就变噪了。

LQR 那一列几乎没动，这本身也是个结论：见第 5 节。

还有一条更实用的：**在新模型上，只改一个 `#define`（把 LQR 环里那个笔误的
1560 改回 1320），LQR 在难度 1.0 档就反超原厂 PID**（219.8 vs 190.4）。
旧模型下这条改动只值 +15 %，现在值 +41 %。见 4.2。

### 2.2 基准车 + 蓝牙遥控 PID 的完整基线

**基准车**指什么外设都不装的那台（`6.LQR/Matlab/parameter_LQR.m`：整车

上面的有两个——`6.LQR/STM32_code` 和 `4.Balanced_Car_base/04.bluetooth_control`，
两者 `APP/` 下都没有额外硬件驱动。这里测后者的 PID：

```
balance_kp=96  balance_kd=0.48  velocity_kp=62  velocity_ki=0.31
turn_kp=14  turn_kd=0.2   （固件存的是 ×100 的整数）
```

复现：`python scripts/bench_pid_baseline.py --episodes 40`

> 可持续速度毫无影响。孪生现在一律照抄固件那个 1560 的 bug，和真板子一致。

**这台车的可持续速度上限是 0.30 m/s**（这是旧电机模型下的数；2026-09-10 换成

边界之外，所以出厂遥控全速前进本来就是会摔的。

⚠️ 这张表是在修掉 `_pid_move_scale` 少乘 2 之后测的。修正前每个速度指令只
兑现一半（比值恒定 0.50），而**静止基准完全看不出来**——那里 `Movement` 恒为
0。`tests/test_twin_baseline.py::test_pid_command_scale` 现在把这个换算钉死了。

**[3] 静止与抗扰品质**（第 10~30 秒稳态，6 个种子）：

| 场景 | 位置跨度 | PWM 换向 | 俯仰 RMS | 速度 RMS | 航向漂移 |
|---|---|---|---|---|---|
| 无扰动 | 0.0092 m | 16.7 /s | 0.20° | 0.097 | 0.0° |
| 侧风 0.35 N@60° | 0.0076 m | 16.6 /s | 0.29° | 0.097 | 2.4° |
| 侧风 + 随机冲击 | 0.1458 m | 7.7 /s | 1.96° | 0.092 | 6.4° |
| 侧风 + 先开 5 秒带转向 | 0.2123 m | 14.3 /s | 0.89° | 0.093 | **33.3°** |

读这张表要注意三件事：

1. **位置守得极死**（0.008 m），但代价是 **PWM 每秒换向 16.7 次**——电机一直在
   左右交替地踹。这是死区决定的：固件对任何非零输出都加 1300 计数补偿，最小
   的一次非零指令就是 45 % 占空比，没有「轻推」这一档。
2. **航向完全没有反馈**。`turn = Turn_Target*Kp + gyro*Kd` 里没有航向状态，
   指令为零时只剩阻尼项。5 分钟长测里它会像风向标一样精确转到 60.2°——正是
   风向——然后停在那儿。任何「松手后朝向不变」的目标都需要补一个作用在航向
   误差上的项，缩放这两个增益做不到。
3. **速度 RMS 恒在 0.097 左右**，四个场景几乎不变。这是死区极限环的幅度，
   扫 108 组增益倍率最低只能到 0.070，且要拿位置跨度涨 20 倍去换。

### 2.1 MuJoCo 后端跑出来的不一样，而且方向是反的

同样 40 回合/档、同样种子、同样 `--imu kalman`，换成
`--backend mujoco`：

| 扰动难度 | 固件 LQR<br>`--imu kalman` | 固件 PID<br>`--imu kalman` | 固件 LQR<br>`--imu lag`（旧） | 固件 PID<br>`--imu lag`（旧） |
|---|---|---|---|---|
| 0.00 | **500.0** | **500.0** | 500.0 | 500.0 |
| 0.25 | **500.0** | **500.0** | 500.0 | **244.4** ← |
| 0.50 | **462.1** | 458.2 | 482.5 | 233.8 |
| 0.75 | **337.8** | 306.9 | 301.3 | 216.2 |
| 1.00 | **311.3** | 242.6 | 230.6 | 203.8 |

先看右边那两列，它们顺带给新模型做了一次验证：**旧的占位姿态模型在 MuJoCo
里让原厂 PID 在难度 0.25 就开始摔**（244.4/500）。一个连轻微扰动都站不住的
「原厂固件 baseline」是不可信的——真车在这个条件下是站得住的。换成 `KF.c`
之后两套固件在 0 和 0.25 档都回到满分，两个后端都是。

也就是说，旧模型在解析后端**高估** PID（352 vs 190），在 MuJoCo 后端**低估**
PID（204 vs 243）。同一个错误的近似，在两个后端上把误差推向了相反的方向——
这正是为什么它值得从源码里抄对，而不是「调一个 tau 让曲线好看」。

**回到左边两列：在 MuJoCo 里 LQR 反过来赢了 PID。** 解析模型里是 PID 赢（190 vs 156）。
不要把这当成噪声抹平——两个后端的差别是具体的：

- 解析模型**根本没有轮子这个自由度**，也就没有打滑。轮子给多少力矩，地面就
  照单全收。MuJoCo 里有真实接触，轮子会打滑。
- LQR 工程的输出级能顶到 **100 % 占空比**（先限幅后加死区，比较值到 3900），
  PID 工程封顶 90.3 %（4.3 节）。这多出来的执行器权限，在一个会打滑、会失去
  接触的世界里更值钱。
- PID 的速度环是对**编码器计数**做无限幅积分的。轮子一打滑，编码器读的是轮子
  在空转，不是车在走——这个环于是在积一个假的位移。LQR 也读同一个编码器，
  但它的速度项权重小得多。

**结论：这两个数字都不是「真值」，真值要真车说了算。** 能说的是：解析模型
偏向 PID，MuJoCo 偏向 LQR，而两者的分歧点正好落在「打滑」这一件事上——所以
**如果要拿一个数去赌，先去真车上量一下地面摩擦**。

难度阶梯是按这辆车重新标定过的，不是沿用通用机器人的。理由：这车整备质量
1.0 kg，轮上峰值力 `2·τ_stall/r = 11.9 N`，其中 `2·τ_coulomb/r = 5.4 N`
先被摩擦吃掉，**净权限只有约 6.5 N**（车重 9.8 N）。通用配置里 20 N 的冲击
对它是算术上不可恢复的，一个全是不可恢复回合的基准什么也测不出来。

## 3. 电机模型是怎么定出来的

固件从没写过电机常数，但它写了一个**只有知道电机才成立的标定**：

```c
velocity_L = Ratio_accel * (x_speed + L_accel/Control_Frequency);  // 2400 counts per m/s
Motor_Left = PWM_Ignore(PWM_Limit(velocity_L, 2600, -2600));       // += 1300
BalanceCar_PWM_Init(2880, 0);                                      // 25 kHz, 周期 2880
```

这条标定成立，等价于电机的稳态「占空比—转速」直线过两个点：

- 占空比 `1300/2880 = 45.1 %` → 转速 0（死区，全部用来克服摩擦）
- 占空比 `100 %` → 转速 `(2880−1300)/2400 = 0.658 m/s`

把轮上力矩写成 `τ = a·(V − b·ω) − τ_coulomb·sign(ω)`，两个点定住 `b` 和
`τ_coulomb`，只剩 `a`（等价于堵转力矩）自由。默认取 0.20 N·m，是这类
12 V / 30:1 减速电机的典型值。

| 量 | 值 | 来源 |
|---|---|---|
| 死区 | 45.1 % 占空比 = 5.42 V | 固件 |
| `b = n·Ke` | 0.336 V·s/rad | 固件反推 |
| `τ_coulomb` | 0.0903 N·m/轮 | 固件反推 |
| **`τ_stall`** | **0.20 N·m/轮** | **唯一的自由参数** |
| 空载转速 | 19.6 rad/s = 0.658 m/s | 固件反推 |

自检里 `commanded speed -> PWM -> steady-state speed is the identity`
这一项验证了整条链路自洽（误差 1e-16）。

**没有实测数据时，`τ_stall` 现在是唯一一个该标定的量。** 上一版把「IMU 卡尔曼
滤波的滞后」列为第二个待标定量——那条已经作废：滤波器本身现在是从 `KF.c`
逐行抄下来的，没有留自由参数（见第 3.5 节）。

## 3.5 姿态滤波：板子上跑的到底是什么

上一版把片上姿态滤波近似成一个 10 ms 的一阶极点，并注明「没有复现」。
现在它被复现了，而且**近似的方向是错的**——不是误差大小的问题，是形状的问题。

`main.c` 里 `GET_Angle_Way = 2`，所以 `Get_Angle()` 走的是这一支：

```c
Pitch = KF_X(accel_y, accel_z, -gyro_x)/PI*180;
```

`KF_X()` 在 `APP/KF/KF.c`，是一个教科书式的两状态卡尔曼（角度 + 陀螺零偏），
Ts = 5 ms：

```
A = [[1, -Ts],[0, 1]]    B = [[Ts],[0]]    C = [[1, 0]]
Q = 1e-10 · I            R = 1e-4          y = atan2(-accel_y, accel_z)
```

注意这个整定。**`Q` 比 `R` 小七个数量级**，滤波器基本不相信加速度计。把
Riccati 递推迭代到收敛：

```
K_inf = [0.003311, -0.000998]      估计器极点 |z| = 0.998343
                                   时间常数   = 3.0 秒
```

**3 秒。** 也就是说，对任何比几秒更快的东西，这个滤波器就是一个纯陀螺积分器，
加速度计只用来修慢漂。三个后果，旧模型三个都搞反了：

1. **俯仰角上根本没有可观的滞后。** 那个 10 ms 极点是在凭空发明一段真板子
   没有的相位损失。
2. 于是 `app_control.c` 里 `gyro_x = (angle_x - last_angle)*200`
   **几乎就是把陀螺原样还原出来**，而不是在对一个滞后信号做差分。第 5 节
   那条「LQR 用角度差分当角速度」的评价要跟着改。
3. 这个滤波器真正糟糕的地方是零偏：3 秒的修正意味着陀螺一漂，误差就直接走进
   角度估计，固件于是平衡到一个错的零位。**那才是这颗 IMU 的真实失效模式**，
   不是滞后。（真车要靠手调 `Mid_Angle` 补，正是这个原因。）

### 片上数字低通：98 Hz，而且是被 DMP 初始化顺手设的

`MPU6050_initialize()` 从没写过 CONFIG 寄存器。但 `bsp.c` 紧接着调
`DMP_Init()`，里面是：

```c
#define DEFAULT_MPU_HZ  (200)                 // mpu6050.c:10
mpu_set_sample_rate(DEFAULT_MPU_HZ);          // -> inv_mpu.c
    ...  mpu_set_lpf(st.chip_cfg.sample_rate >> 1);   // = mpu_set_lpf(100)
    ...  100 >= 98  ->  INV_FILTER_98HZ
```

所以 5 ms 中断读到的寄存器**不是原始值**：陀螺和加速度计都在片内被 98 Hz /
94 Hz 滤过（数据手册群延迟 2.8 ms / 3.0 ms），寄存器按 200 Hz 更新。

这一条不是锦上添花，是必需的。没有它，仿真里 100 Hz 以上的机架抖动会**混叠**
进卡尔曼的新息，把零偏状态推成随机游走——实测能在 5 秒内让 MuJoCo 里的 LQR
翻车。真板子上那些能量在进寄存器之前就被滤掉了。孪生里 DLPF 跑在积分步长
（800 Hz）上，不是控制步长上，正是为了不重新引入同一个混叠。

### 加速度计不测重力，它测比力

IMU 装在轴心上方 `l_com = 38.3 mm`，量的是比力，所以

```
accel_y = v̇·cosθ + l·θ̈ − g·sinθ
accel_z = v̇·sinθ − l·θ̇² + g·cosθ
```

也就是说，**车一加速，加速度计对「下」的判断就是错的**——而平衡车加速的时刻
恰恰就是它在纠偏的时刻。2 m/s² 的前向加速度会被读成 −11.5° 的后仰。这就是
为什么固件那个看着离谱的 `R >> Q` 其实站得住脚。自检里有这一条。

`--imu lag` 保留了旧的占位模型，按它发表过的数字仍然能复现。

## 4. 复现的两个固件 bug，以及它们值多少步

### 4.1 偏航率估计小了 10⁶ 倍

```c
gyro_z = (Encoder_Right-Encoder_Left)/Wheel_spacing/1000*PI*Diameter_67/1000/1560*Control_Frequency;
```

`Wheel_spacing` 是 161.0 **毫米**，换算成米应该是 `/(Wheel_spacing/1000)`，
但代码写成了 `/Wheel_spacing/1000`，即除以 161000 而不是 0.161。

**偏航反馈实际上是死的。**转向仍然能用——但走的是同一表达式里
`Target_gyro_z` 那一半，是纯开环。

**修掉它反而更糟。** 这一版重跑（40 回合/档，`--imu kalman --ablate`）：

| 配置 | 难度 0.50 | 难度 1.00 |
|---|---|---|
| 原样（偏航反馈被缩放杀死） | **374.0** | **155.8** |
| 修偏航标度，K5/K6 照抄固件 | 79.6 | 60.8 |
| 修偏航标度 + 修编码器线数 | 69.2 | 49.7 |

**修完的摔倒率是 100 %**，两档都是。下面这组更细的拆解是在旧姿态模型上跑的
（难度 0.5，20 回合），绝对值会变，但三行之间的关系是由量化台阶决定的，
和姿态滤波无关：

| 配置 | 存活步数 |
|---|---|
| 原样（偏航反馈被缩放杀死） | **441.0** |
| 修标度，K5/K6 照抄固件 | 80.4 |
| 修标度 + K5=K6=0 | **441.0** ← 和原样一模一样 |
| 修标度 + K5/K6 缩到 1/10 | 396.1 |

第三行证明了这个 bug**精确等价于关掉偏航反馈**。再拆开看：

| 配置 | 存活步数 |
|---|---|
| K5=15.81, K6=15.81 | 80.4 |
| K5=0, K6=15.81（只留速率） | 434.4 |
| K5=15.81, K6=0（只留积分） | 380.8 |

**两项单独都不致命，合起来才崩。** 原因是偏航估计的量化台阶极粗：编码器差
1 个计数就是 **0.168 rad/s**，而 `angle_z` 又对这个量化噪声做**无限幅积分**。
在量化信号上放一对 PI，就是经典的积分饱和/极限环配方。

结论：这个 bug 是**承重的**。不重新整定 K5/K6（或给偏航估计加滤波）就去
「修正」它，车会变得难开得多。这正是数字孪生的价值——在仿真里发现，而不是
把一个坏固件刷进真车才发现。

### 4.2 LQR 环把速度读低了 15 %

LQR 用 1560 counts/rev，而 `app_motor.h` 定义的编码器是
`4 × 11 × 30 = 1320`。凡是 LQR 用到速度和位置的地方都乘了 0.846。

**这条的分量在这一版翻了一倍还多。** 旧模型下修掉它只是「小幅有益」
（0.5 档 450.8 → 486.6，1.0 档 168.3 → 193.0）。换成板子真跑的姿态滤波之后
（40 回合/档，评测种子 20000，`--imu kalman --ablate`）：

| 配置 | 难度 0.50 | 难度 1.00 |
|---|---|---|
| 固件 LQR 原样 | 374.0 | 155.8 |
| **固件 LQR + 修编码器线数** | **475.8**（+27 %） | **219.8**（+41 %） |
| 固件 PID 原样（对照） | 486.8 | 190.4 |

看最后两行：**只改一个 `#define`，LQR 在难度 1.0 档就反超了原厂 PID**
（219.8 vs 190.4）。这是整个孪生里性价比最高的一处改动——一行代码，不用重新
整定任何增益，因为 1320 才是这块编码器的真实线数，1560 是笔误。

（0.5 档仍差一点点，486.8 vs 475.8，在标准差里。）

### 4.3 两套工程的输出级顺序不同（不是 bug，但影响很大）

- **LQR 工程**：先限幅 ±2600，**再**加 1300 死区 → 比较值到 3900，硬件钉在
  **100 % 占空比**
- **PID 工程**：先加死区，**再**限幅 ±2600 → 上限 **90.3 % 占空比**

LQR 那辆车的执行器权限实实在在更大。两种顺序都照抄了。

## 5. 还有哪些是「照抄的怪东西」

- **俯仰角速度是角度的一阶差分**，不是陀螺：
  `gyro_x = (angle_x - last_angle) * 200`。
  **这条的评价在这一版被推翻了。** 既然卡尔曼滤波实质是个纯陀螺积分器
  （第 3.5 节），差分回来的东西就约等于陀螺本身，只是额外混进了
  `K0/Ts = 0.66` 倍的加速度计新息。所以它并不像看上去那么糟——旧的
  `imu_filter_tau=10 ms` 模型才是让它显得糟的原因。
  连带地，WINDOWS.md 里「`K4 ×0.64` 是因为那个角速度带滞后」这条解释也
  作废了：CEM 是在旧模型上搜的，那个解释拟合的是占位模型的滞后，不是真车。
  **要在新模型上重搜一遍才作数。**
- **PID 工程的增益作用在原始 LSB 上**：`Gyro_Balance = -Gyro_X` 是未换算的
  16 位寄存器值，所以 `Balance_Kd = 0.48` 的单位是「PWM 计数 / LSB」
  = 7.9 计数/(°/s)。传 rad/s 进去会差 940 倍。
- **机械零位**：LQR balance 到 0.0349 rad，PID balance 到 1°，因为真车 IMU
  没装平。孪生把这个建模成传感器安装误差
  （`measured = true + mount_offset`，默认等于固件自己的设定值），否则仿真里
  车会永久前倾并跑掉。想看标定失准的代价，把 `mount_offset_deg` 调开即可。
- **40° 关电机**是这辆车真正的失败判据，所以 `pitch_fail` 用的是 40° 而不是
  仿真里随便定的阈值。

### 6.4 修掉的一个孪生 bug：打滑时反电动势失效

MuJoCo 后端里电机模型拿的轮速是从车身速度反推的：

```python
omega = (v ∓ track/2 · yaw_rate) / r_wheel        # 假设纯滚动
```

地面抓得住时这没问题。地面一滑就完全不成立，而且后果不小：电机模型靠这个
转速算反电动势，于是一个**实际转到 80 rad/s 的轮子被告知它只转了 6 rad/s**，
继续输出接近堵转的力矩，转速无限爬升，接触求解器开始抖，车在 0.16 秒内飞出去。

看上去像「摩擦一低就必然摔」，其实是电机模型被喂了错的转速。现在 MuJoCo 后端
直接读轮关节自己的速度（`_wheel_speeds()`），解析模型仍用原式——它压根没有轮子
这个自由度。修完之后摩擦扫描是这样的（LQR，20 秒，无其他扰动）：

| 地面 μ | 1.0 | 0.8 | 0.6 | 0.4 | 0.2 | 0.1 | 0.05 |
|---|---|---|---|---|---|---|---|
| 存活步数 | 500 | 500 | 500 | 500 | 500 | 500 | **37** |

原厂 PID 的悬崖在 μ≈0.1，比 LQR 早一档。这是个能用的曲线；修之前 μ=0.6
就已经全灭了。

## 7. 完整对比流程（原型 vs 调参）

三条命令。**关键是调参种子和评测种子不相交**，否则测的是背题不是控制。

```bash
# 1. 看原型的 baseline（评测种子从 20000 开始）
python scripts/bench_twin_baseline.py --episodes 40

# 2. 搜一组参数（调参种子从 70000 开始，和上面不重叠）
python scripts/tune_twin_baseline.py --firmware stm32_lqr --out tuned_lqr.json   # 约 15 分钟
python scripts/tune_twin_baseline.py --firmware stm32_pid --out tuned_pid.json

# 3. 在**没见过的种子**上复评，原型和调参并排打印
python scripts/bench_twin_baseline.py --params tuned_lqr.json --episodes 40
```

`tune_twin_baseline.py` 搜的就是**要烧进板子的那几个常数**（LQR 的 6 个 K，或 PID 的
6 个增益），不是神经网络——结果可以直接替换 `app_control.c` 里的数字。
搜索空间是相对固件值的**对数倍数**，所以 `x = 0` 就是原型，任何提升都是
实打实赢过了一个能用的控制器。

`mid_angle_deg` 故意不参与搜索：它是 IMU 装歪多少的物理量，让优化器动它
只是在拟合仿真自己的安装偏置。

### 实测结果（LQR，CEM 12 轮，held-out 40 回合/档）

> ⚠ **下表的数字全部作废，产物 `tuned_lqr.json` 也已于 2026-09-10 删除。**
> 它跑在旧的一阶滞后姿态模型上（相当于 `--imu lag`）；第 3.5 节之后姿态链路
> 换成了板子真跑的 `KF.c`，此后电机模型、`tau_max`、质量、几何、MuJoCo 积分器
> 又全部改过。表留在这里，只是因为它下面那两条方法论结论（过拟合的量、
> 架构 vs 参数）跟这些改动无关，仍然成立。

| 难度 | 固件 LQR 原型 | CEM 调参 | 固件 PID 原型 |
|---|---|---|---|
| 0.50 | 460.5 | **476.6** | **500.0** |
| 0.75 | 249.3 | **330.0** | **464.5** |
| 1.00 | 149.3 | **221.5** | **349.4** |

调出来的增益：`K2 x1.79`（速度反馈加重）、`K6 x2.23`（偏航率——但它作用在被
bug 缩掉 10⁶ 倍的信号上，所以实际是空转，见 4.1）、`K4 x0.64`（俯仰阻尼减小，
因为那个角速度是角度差分出来的、本身就滞后）、`K3 x1.00`（俯仰刚度一动没动，
说明固件那个值本来就对）。

**两个必须看清的点：**

1. **调参集上 189 → 357（+89%），held-out 上只有 +48%。** 这个落差就是过拟合
   的量。只报调参集分数是自欺欺人。
2. **调完的 LQR 仍然打不过原厂 PID**（330 vs 465）。所以这辆车上，PID 架构本身
   比 LQR 架构好，不是参数没调好的问题。要超过 PID，得动结构（比如给 LQR 换上
   真陀螺而不是角度差分），不是继续搜参数。

## 9. 拿它和 RL / LLM 对比时的注意事项

1. **工程里不附带任何训练好的权重，这是故意的。** 原来那几个
   `policy_stm32_*.npz` 是在旧的一阶滞后姿态模型上训的，还有一个
   `policy_v2.npz` 是在通用机器人（1.7 kg、质心 120 mm、执行器强得多）上训的。
   姿态链路换成 `KF.c` 之后观测分布变了（PID 那一侧尤其明显，第 2 节），
   留着它们只会让人误以为有现成结果可用，所以清掉了。
2. **`tuned_lqr.json` 已于 2026-09-10 删除**（原先只是标记过期）。它的
   `_provenance.imu_model = "lag"` —— 那个一阶滞后占位模型已被推翻，加上
   此后电机模型、`tau_max`、质量、几何、MuJoCo 积分器全部改过，那组增益
   没有任何可复现的语义了。原始数值和作废理由存在
   `runs_stm32/DELETED_2026-09-10.md`。要重跑：

   ```bash
   python scripts/train_stm32_rl.py --steps 3000000 --n-envs 8            # PPO
   python scripts/tune_twin_baseline.py --firmware stm32_lqr --out tuned_lqr.json  # CEM
   ```

   注意是 `scripts/train_stm32_rl.py`，**不是** `balance_bot.train_sb3`——
   后者训的是底层那套通用机器人（33 维观测、9 个增益），导出格式这边读不了。

   重训出来的 `.npz` 放在工程根目录，`sim_gui.py` 会自动把它列进
   「控制模型」下拉框。
3. **同种子对齐**。`bench_twin_baseline.py` 已经保证了，别换成各跑各的随机种子。
4. **报告最差回合，不要只报均值。** 存活步数的分布是长尾的（标准差经常
   接近均值），只看均值会把「偶尔灾难性失败」的策略判成好策略。
5. **难度 0 和 0.25 档两套固件都是满分**，不要在那两档上做优化——没有可赢的
   空间，测出来的差异全是噪声。真正有区分度的是 0.5 以上。

### 10.3 三个结构性发现（不是调参，是模型缺件）

1. **卡尔曼零偏播种**。固件上电时 `P` 是单位阵，几拍就学到 +2 °/s 的陀螺零偏；
   孪生每次 reset 却把零偏估计写死 0，于是角度一直偏，表现为 40 mm 游走加
   12.5 Hz 振荡。这一条修好，综合误差从 0.99 掉到 0.089。
2. **滚动阻力要 condim 6**。MJCF 里写了滚动摩擦系数，但 `condim=3` 的接触根本
   不算它——写了等于没写。改成 6 之后慢漂移才压得住。
3. **左右两个电机不是一对**，死区差 98.6 计数。真车左右编码器幅值差 20%
   （0.39 / 0.47 计数），两边不同时"踢"，才凑得出真车陀螺 3–6 Hz 与 6–12 Hz
   对半开的频谱；对称孪生的能量全挤在 4.3 Hz 基频上。试过的其他结构
   （轮胎滚阻、转子黏滑、齿轮刚度/阻尼、随轮速振动）都动不了这个分配。

### 10.6 训练时按这些条件打折

按预期差距排序，前四条**不要**拿孪生当定量依据：

1. **快速激励 / 高增益**：幅度差 30–40%，共振频率低 20%（已实测）。
2. **车速 > 0.2 m/s**：力矩-转速曲线完全没被约束。堵转在近零速拟合，反电动势
   系数直接用规格书空载转速，阻尼项的 tanh 在 0.012 m/s 就饱和了。
3. **负重 ≥ 1 kg**：重新拟合后一次没验过；孪生也没有电池内阻压降模型，
   大电流时真车电压会掉、力矩跟着掉，孪生不会，越重越乐观。
4. **转向**：加滚动阻力时把 condim 从 3 改成 6，**同时打开了扭转摩擦**（原来是
   死的），转向阻力变了且从没对过真车。旧的"高负重难转向"结论要重测。
5. **打滑 / 碰撞 / 斜坡**：地面 μ 在静止工况下辨识不出来（0.7–1.5 综合误差都
   在 0.005–0.015），0.90 是按花纹橡胶胎的物理值定的，不是测出来的。

中等：左右死区差在行驶时会变成持续跑偏（等效两边力矩差 7%，未核）；随轮速的
陀螺振动项是 10 倍外推；滚动阻力按常系数处理。

可忽略：齿轮间隙（受载后齿面贴住）、死区正反不对称（相对 1380 计数是小量）、
IMU 装歪、编码器量化、空气阻力、转子静摩擦（转起来按 exp 衰减）。

**给训练的建议**：上面 1–5 条对应的量在域随机化里要给足范围，别按孪生的单点
值训。静止和小扰动可以信孪生的绝对值；大扰动、高速、负重只能信趋势。

### 10.7 要把缺口补上，最划算的三个测量

1. **定速台阶**：几档固定 PWM 各跑几秒，记稳态轮速 → 一次标定整条力矩-转速
   曲线，解决第 2 条，顺带修正第 1 条的惯量。
2. **直线跑偏**：直线 3 米量横向偏移 → 标定左右不对称。
3. **原地转向 + 负重转向** → 解决第 3、4 条。

固件侧 `tune_io.c` 已经能录，加个定速指令即可。
